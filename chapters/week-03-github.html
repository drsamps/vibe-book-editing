GitHub: Save Points, Review and the Human in the Loop — Vibe Programming, Session 3

Adapted and simplified from the first half of Scott Murff’s chapter Version Control, Environments, and Deploys, in his textbook Intro to Product Management. The ideas are his. The wording and the business examples were written for these readings.

Reading time: about 20 minutes. Class opens with a short quiz on this reading.

Learning objectives

By the end of this session you can:

  1. Explain what a commit is and what makes one useful to return to.
  2. Say what changes when work moves from your computer to GitHub, and what must never go there.
  3. Describe the steps of a pull request, from a new branch to the live app.
  4. Review a change before it goes live, using the list of changes and the preview.
  5. Explain why small changes merged often are safer than large ones, and what going back cannot undo.

The big idea: a way back and a gate

In session 1 you sorted the agent’s actions into three groups. Group 2 was the uncomfortable one. When the agent runs a command that deletes or moves files, rewinding to a checkpoint cannot help. You needed a save point, and the reading promised one in session 3.

In session 2 you learned that your project is a set of files. You also learned that the live copy of your app runs on a hosting company’s computers.

This session connects the two. The agent can change your project many times a day. If you cannot safely change your app, you no longer control it.

Here is the main point of the session: version control gives you a way back to any earlier state of your project, and a gate every change passes before users see it.

Version control is a system that records every change to a set of files. The one your project uses is called Git. GitHub is a website that stores a copy of your project and its history online, for backup, sharing and review.

You will rarely type a Git command. The agent does that when you ask in plain English. Your job is to know what each step means, and to be the person at the gate.

Commits: your save points

A commit is a saved snapshot of your whole project, with a message that says what changed.

When you ask the agent to save a save point, it makes a commit. The commit records every file in the project as it is at that moment. Git keeps every commit, in order, and you can return to any of them.

This is the safety net for session 1’s group 2. If the agent deletes the wrong folder, Git can bring back every file as it was in your last commit. A file you never committed is gone.

A manufacturer controls its drawings the same way. Each released version of a drawing gets a revision letter and a change note. Anyone can pull revision B and see exactly what the part looked like then. A commit is a revision of your whole project, and its message is the change note.

The message matters as much as the snapshot. Compare two histories of the same afternoon.

Useful history Useless history
Add days-of-stock column to sales dashboard updates
Show days of stock in red below 14 more changes
Leave cancelled orders out of sales numbers fix

In the first history you can find the exact point you want to return to. In the second you cannot.

Worked example. You plan to have the agent delete the folder of old sample data. First you say, “Save a save point called ‘Before removing old sample data.’” The agent deletes the folder, and one file the product screen needed goes with it. You say, “Bring back the project as it was at the last save point.” The file returns. Without the commit, it would be gone.

Two habits make commits useful:

  • Commit small. One finished piece of work per commit. A commit that mixes five changes is hard to undo without losing four good ones.
  • Commit before risk. Make a save point before any group 2 action.

Rule of thumb: if you would be upset to lose it, commit it.

Two copies: your computer and GitHub

A commit stays on your computer until you push it. A push leaves your computer.

Your project lives in two places. One copy, with its full history, is on your computer. The other is on GitHub.

  • A push copies your new commits from your computer to GitHub.
  • A pull copies new commits from GitHub to your computer.

Now apply session 1’s blast radius. A commit is local. Nobody else sees it, and it can be undone, so the agent can commit freely. A push is different. It reaches GitHub, and depending on where it lands, it can update your live app. A push is a group 3 action.

That gives you a standing rule for your instruction file: commit freely, and push only when I say so.

An advertising team works the same way. A designer can revise an ad on their own computer all day. Nothing reaches customers until the ad is sent to the printer. A commit is a saved revision. A push is sending it out.

What must never be pushed

Session 2 introduced .env.local, the file that holds your secret keys. It must never reach GitHub, because a secret in a public project is published.

Git handles this with a file named .gitignore. It is a list of files that Git must not track. Files on that list are never committed, so they are never pushed. Your project’s .gitignore should include your secrets file.

You can check in one sentence: “Which files in this project are ignored by Git, and why is each one ignored?” If the secrets file is not on the list, have the agent fix that before the next commit.

Rule of thumb: a commit is a note to yourself. A push is a message to the world.

Branches: a side line for each change

A branch lets you build and test a change without touching the version your users see.

Your project has one official line of commits, named main. Your live app is built from main. Every new commit that reaches main on GitHub is published to the live app.

A branch is a separate line of commits that starts from main and does not change it. You can commit to a branch all afternoon. main and the live app stay exactly as they were.

A restaurant does this with a test kitchen. A new dish is tried in the back while the regular menu keeps serving customers. If the trial fails, diners never knew. If it works, the dish goes on the menu.

Worked example. In the example shop, the owner wants to keep notes on each customer. You say, “Start a new branch called customer-notes and do this work there.” The agent adds a notes box to the customer screen and saves two commits on the branch. Anyone using the live app sees no change. The work is real, saved and out of the way.

Give each branch one task and a name that says what the task is. customer-notes tells you what is on it. test2 does not.

Rule of thumb: one task, one branch.

The pull request: the gate

A pull request holds a change at the gate while it is checked, previewed and reviewed. Nothing reaches the live app until someone merges it.

A pull request is a page on GitHub that asks to add one branch’s commits to main. Adding them is called a merge. While the pull request is open, three things happen.

  1. Checks run. GitHub runs a set of automated checks on the change and marks the pull request with a green check or a red X. Session 5 covers what the checks test.
  2. A preview is built. The hosting company builds a working copy of the app with this change, at its own web address. This is the preview. It is separate from the live app.
  3. Someone reviews. A person reads what changed, clicks through the preview, and then approves or sends the work back.

Here is one change from start to finish.

Step What happens Has the live app changed?
1. Branch The agent creates the branch customer-notes. No
2. Commit The agent builds the feature and commits it to the branch. No
3. Push and open The agent pushes the branch to GitHub and opens a pull request. No
4. Checks and preview The checks run, and a preview is built. No
5. Review You read the changes and try the preview. No
6. Merge You merge the pull request. The commits join main. About to
7. Publish The hosting company publishes the new main to the live app. Yes

A company handles a new policy the same way. The change is written up, reviewed by the people it affects and checked by legal. Only after sign-off is it announced to employees.

What to read in a review

The page for a pull request shows the diff: every line added, removed or changed, compared with main. You do not read code, but you can still review a diff in three ways.

  • Read the list of changed files. Session 2 taught you to read file names. Did the agent change a file your request had nothing to do with?
  • Ask a fresh conversation to review it. Start a new conversation with the agent. Ask it to explain the diff in plain English and to flag anything outside the request. A fresh conversation catches more than the one that wrote the change.
  • Try the preview. Use the feature the way a customer or the owner would, with session 1’s edge cases.

Worked example. You open the pull request for customer-notes. The preview looks right. Notes save and reappear. Then you read the list of changed files. One of them is the server file that handles cancelling orders. Your request had nothing to do with cancelling.

You ask a fresh conversation to explain. It reports that the agent removed the server check that refuses to cancel a shipped order. The agent had hit an error along the way and removed the check to make the error go away.

Remember session 2. That server check is what stops a shipped order from being cancelled. The grey Cancel button is still there, so the preview looks perfect. The problem is invisible in the running app and plain in the diff.

You send the work back. The agent restores the check in a new commit, the pull request updates, and only then do you merge. Without the pull request, the missing check would have gone straight to the live app.

You are the human in the loop

Three facts about the gate are worth knowing.

  • A red X does not lock the gate. Unless the project is set up to require passing checks, GitHub still lets you merge. Look before you click.
  • You cannot approve your own pull request on GitHub. When you work alone, the review is you reading the changes and the preview before you merge.
  • The preview may share the live database. A preview is a separate copy of the app. It may still read and write the same data as the live app. Session 8 covers how to give it data of its own.

Merging is a group 3 action. It is the moment a change leaves your control. The agent should never merge on its own.

Rule of thumb: the preview shows you what the change does. The diff shows you what else it did.

Keep changes small and merge them often

A small change merged within a day or two is easier to review and undo, and less likely to collide with other work.

A branch should be short-lived. Finish the task, merge it within a day or two and delete the branch. Then start the next branch from the newest main.

The opposite is a long-lived branch, kept open for a week or more until a big feature is finished. Two things go wrong.

First, the branch drifts. main keeps changing while the branch is open. When the branch finally comes back, Git has to combine both sets of changes. Where both sides changed the same lines, Git stops with a merge conflict. Someone has to decide by hand which version is right.

Second, the diff becomes too large to review. An agent can write a thousand changed lines in a few minutes. The removed check in the last example is easy to spot in a list of three changed files. It is easy to miss in a list of sixty.

Lean manufacturing makes the same point with batch sizes. A defect in a batch of ten is found the same day, and ten units are affected. A defect in a batch of ten thousand is found weeks later.

Worked example. The shop owner wants a reorder suggestion on the dashboard, plus a monthly sales report, plus customer notes. As one branch, that is a week of work and one enormous review. As three branches, each is a day of work and a short review. If the report turns out wrong, you undo the report and keep the other two.

Is a branch always required? Committing straight to main skips the gate. There is no preview, and nobody reads the diff before users see the change. It is reasonable only for a small change, such as a typo, when you work alone and have checked the app first. In this course, use a branch and a pull request for every change.

Rule of thumb: if a change takes more than a day or two, split it.

Going back, and what going back cannot undo

You can undo a change to your project’s files. You cannot undo what the change already did to your data.

Version control gives you two ways back.

Situation What you ask for What happens
The work is not pushed yet “Bring the project back to the last save point.” Your files return to that commit.
A bad change was already merged “Revert that commit.” The agent makes a new commit that undoes the old one. Merging it publishes the undo.

A revert does not erase history. The bad commit and the commit that undoes it both stay in the record. That is deliberate. You can always see what happened.

Small merges make this easy. If the last merge changed one thing, you know which commit to revert.

Now the limit. Commits record your project’s files. They do not record the rows in your database. Suppose a bad change went live for an hour and marked forty orders as shipped. Reverting the change restores the old code. The forty rows stay wrong.

A publisher knows this problem. It can fix a misprint for the next printing in a minute. The copies already sold still carry the misprint.

So match your caution to what the change touches. A change to a screen can be reverted cleanly. A change that alters or deletes stored data deserves a backup first, and a careful review at the gate. Session 6 covers the database. Session 8 covers undoing a bad publish quickly.

Rule of thumb: code has an undo. Data needs a backup.

Plain-English requests for this session

You direct all of this in ordinary sentences. The Git words are in the right-hand column so you can follow the agent’s reports.

What you say Git word for it
“Save a save point with a message that says what changed.” Commit
“Show my last ten save points, with one line on each.” Log
“Start a new branch for this task.” Branch
“Push this branch to GitHub and open a pull request.” Push, pull request
“Revert that commit.” Revert
