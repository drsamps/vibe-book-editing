Testing: How Do You Know It Works? — Vibe Programming, Session 5

Adapted and simplified from two of Scott Murff’s chapters, Tests and Tech Debt and The Browser, Developer Tools, and Claude in Chrome, in his textbook Intro to Product Management. The ideas are his. The wording and the business examples were written for these readings.

Reading time: about 20 minutes. Class opens with a short quiz on this reading.

Learning objectives

By the end of this session you can:

  1. Explain what an automated test is and read a list of test names as a statement of what is protected.
  2. Tell apart the three sizes of test, and explain what a passing result does not tell you.
  3. Direct the agent to test what matters, and spot a test that was changed to pass.
  4. Explain why you run an AI code review before you send changes to GitHub.
  5. Gather your own evidence with the reload test, the browser’s developer tools and the app’s logs.

The big idea: every change can break something that used to work

Since session 1 you have checked the agent’s work by hand. You look at what changed, run the app and try the awkward cases. That works for the feature you just asked for.

It does not cover everything else. The example shop now has a dashboard, shipping, cancelling and customer notes, and your own app has grown the same way. The agent changes it many times a day, and any change can break something that used to work. A problem like that is called a regression. You cannot click through the whole app after every change.

Here is the main point of the session: an automated test checks one behavior in seconds, every time the app changes. A passing test proves only what someone thought to check.

You will not write tests. The agent writes them. Your job is to decide what must be tested and to read what the tests claim. You also need to know what a green check mark is worth.

What a test is

A test is a short program that runs part of your app with a chosen input and compares the result with the expected answer.

Every test has the same three steps.

  1. Choose an input.
  2. Run the app’s code on it.
  3. State the answer it must give.

If the result matches the expected answer, the test passes. If not, it fails, and the report shows both values so you can see what changed. All the tests in a project together are called the test suite. People say the suite is “green” when every test passes and “red” when any test fails.

A machine shop uses a go/no-go gauge the same way. The gauge is made to a known size. A part either fits it or does not. Nobody has to measure and judge each time.

Worked example. In session 1, the example shop marked an order as shipped late when it shipped on its promised date. Here is a test for that rule, in plain words.

Step For the on-time rule
Choose an input An order promised for March 10 and shipped on March 10
Run the code Ask the app whether this order shipped on time
State the answer It must say “on time”

Each test has a name, and the name is a sentence saying what the app must do. You cannot read the code inside a test. You can read the names, and a list of names reads like a specification:

  • An order shipped on its promised date is on time.
  • An order shipped one day late is late.
  • A cancelled order is left out of every sales number.
  • A shipped order cannot be cancelled.
  • A product with no sales shows no days of stock left.

That list tells you what is protected. It also tells you what is not. If “an order shipped in two parts” is missing from the list, nothing is checking it.

Rule of thumb: ask the agent for the list of test names, and read it for what is missing.

Three sizes of test

Tests differ in how much of the real app each one runs. The more it runs, the slower it is and the more kinds of failure it can find.

Session 2 gave you three places: browser, server and database. The three sizes of test line up with them.

Size What it runs Example in your app What it would catch Speed
Unit test One rule, alone. No browser, no server, no database. The on-time rule, given two dates A wrong rule, such as “before” where it should say “on or before” Thousandths of a second
Integration test Several real pieces together, such as the server and a database Shipping order 2042, then reading the database to see what was saved A save that fails, or saves the wrong values Slower
End-to-end test The whole app, through a real browser, clicking as a user would Open the app, ship an order and check that the dashboard changes A step a user cannot finish, such as a button that does nothing Seconds each

A restaurant checks food at the same three levels. The cook tastes the sauce on its own. The chef checks each plate as it is put together. Then a manager eats the whole meal the way a customer would. Each level catches problems the level below cannot see.

The usual advice is to have many unit tests, fewer integration tests and only a few end-to-end tests. The large ones are slow, and they fail for more reasons.

Two details matter to you as a manager.

  • Tests need their own database. Integration and end-to-end tests create and delete rows. They must run against a separate test database, never the live one.
  • Red in the middle is normal. The agent runs the suite after its own edits, reads the failures and fixes them. What matters is the last run before it says it is done.

The checks on a pull request

In session 3, a pull request showed a green check or a red X. Now you know what ran. The usual set has four checks.

Check What it does
Tests Runs the test suite
Type check Reads the code to confirm each value is the kind of data the code expects
Lint Reads the code and flags likely mistakes
Build Makes the same finished version the hosting company would make

Tests run your code. The type check and the lint only read it, so they are fast and catch different mistakes. The build is the last gate. If it fails here, publishing would fail too.

Rule of thumb: a rule gets a unit test. A path that users depend on gets one end-to-end test.

What a passing result does not tell you

A green suite means that none of the checks someone wrote failed. It says nothing about what nobody checked.

Four limits are worth knowing.

  • Untested behavior is unchecked. If no test covers partial shipments, the suite can be fully green while partial shipments are broken.
  • The tests share the author’s understanding. If the agent misunderstood your rule, it writes code and tests with the same mistake, and they agree with each other. You saw this in session 1.
  • Tests do not tell you whether the feature is the right one, or whether people can use it. That takes the usability testing from session 4.
  • A test can be changed to pass. This is the one to watch.

A health inspection has the same limits. “Passed inspection” means the restaurant passed the items on the checklist. Anything not on the checklist was never looked at. And there are two ways to pass a failing item: fix the kitchen, or loosen the checklist.

Worked example. You ask the agent to give pre-orders of a new seasonal flavor three extra days before they count as late. Afterward the suite is green. In the pull request, you read the list of changed files and see that a test file changed too. You ask a fresh conversation with the agent to explain.

It reports that the test “an order shipped one day late is late” used to expect “late.” It now expects “on time.” The agent’s change broke the rule for every order. Instead of fixing its code, it changed the expected answer.

An agent told to “make the tests pass” has three shortcuts. It can change the expected answer, delete the test, or mark the test to be skipped. All three turn the suite green. None of them fixes anything.

Rule of thumb: when a change touches both the app and its tests, review the test changes first. A changed expected answer, a deleted test or a skipped test needs a reason.

Your part in testing

You decide what must never break, and you make the agent prove each bug is fixed.

Asking for “tests” with no target gets you tests of whatever was easiest to test. Aim the effort.

A quality engineer does not inspect every dimension of every part. The control plan names the characteristics that are critical to quality, and those get checked every time.

Five habits cover your part.

  1. Ask for tests on what matters. In your app, that means any score or number a manager will act on. It also means anything that changes stored data, and the main path through the app.
  2. Read the test names as a specification. A missing behavior in the list is a missing check.
  3. Confirm the suite ran before you merge. Look at the checks on the pull request, or ask the agent to run the suite and show you the last result.
  4. Read test changes first in any review, as in the example above.
  5. For every bug, ask for a regression test that fails first.

The fifth habit needs a word of explanation. A regression test is a test written for a bug you fixed, so the bug cannot come back unnoticed. Ask for it in a particular order.

Worked example. The owner reports that order 2041 was cancelled after it shipped. You tell the agent, “Before you fix anything, write a test that reproduces this, and show it to me failing.” The agent writes “a shipped order cannot be cancelled.” It runs the test, and the test fails. Then it fixes the code, and the same test passes.

The failing run proves the test can detect the bug. The passing run proves the fix works. A test you never saw fail might not be checking anything.

One more caution. The worst regressions come from changing something that several features share. Suppose the agent changes how dates are handled. That touches the on-time rule, the weekly late-shipments report and the units-sold-per-week calculation. Before it finishes, ask it to list every feature that uses what it changed, and to test each one.

Rule of thumb: no bug is fixed until a test that failed now passes.

A second reader: AI code review

Before you send changes to GitHub, have the agent run a code review that reads them for mistakes.

Tests check what someone thought to check. A code review is a careful reading of a set of changes, looking for mistakes that no test was written for. It looks for a rule that misses a case, a save that can fail without warning, or a change that breaks another feature.

Code review used to need a second programmer, who read each pull request line by line. You could not do that job. An agent can. Claude Code has a code review built in.

What you want How When to use it
Review your changes for mistakes Type /code-review in the message box, or ask “Run a code review of my changes” Before you send changes to GitHub

With nothing added after it, the review reads the changes you have not yet sent to GitHub. It reports what it found: where each problem is and why it matters. It does not change anything on its own. In the desktop app the findings arrive as a card, with buttons to fix one finding or all of them.

Your part is the same as in session 1. Read the list. Ask the agent to explain any finding you do not understand. Have it fix the ones you agree with. Then run the tests again, because a fix is a change too.

Expect the review to find something. Even a change that passes every test usually has a finding worth fixing.

Accountants work the same way. Many companies require a second person to review a journal entry before it is posted to the books. The person who wrote the entry is the one least likely to see its mistake.

Rule of thumb: review before you send. Fix what you agree with, then test again.

Look for yourself

Some evidence you can gather yourself in under a minute, without the agent.

The reload test

An app can keep data in three places, and they are not equally permanent.

Place How long it lasts Who can reach it
Page memory Until the page reloads or the tab closes This tab only
Browser storage Until the user clears their browser data This one browser, on this one device
Database Until someone deletes it Every device and user you allow

The rule follows from the table. If data must follow the user to another device, be shared with others or be trusted, it belongs in the database. The copy in the database is the one that counts.

A store knows this as the gap between the system count and the shelf. You do not trust the count on the screen until someone has checked what is actually there.

So here is the simplest test you can run. Enter something, reload the page, and see whether it is still there. If a customer note vanishes on reload, it was only in page memory and was never saved. Then open the app on your phone. If the note is on your computer but not your phone, it was saved in the browser, not the database.

The evidence panels

Session 2 introduced developer tools, the panel built into every browser. In Chrome you open it with the F12 key on Windows, or Command, Option and I on a Mac. Two of its tabs give you evidence.

Tab The question it answers Use it when
Console Did the app’s code hit an error? A screen is blank, or a button does nothing. Errors appear in red.
Network What requests went out, and what came back? Something did not save or load.

Each row in the Network tab is one request, with a number called a status code. You need only three ranges. Codes in the 200s mean the request worked. Codes in the 400s mean the request was wrong or was refused. Codes in the 500s mean the server failed.

When you report a problem to the agent, this is your evidence. “Shipping order 2042 does nothing” is a weak report. Paste the red error from the Console and the status code of the failed request, and the agent starts from facts instead of guesses.

The app’s own record: logs

A log is a running record your app writes as it works: one line for each important action or error, with the time. Developer tools show only what happens in your own browser, right now. A log shows what happened on the server, for every user, after the fact.

Your app writes only what it was told to write. So ask for it: “On the server, write a log line each time an order is shipped or cancelled, and each time a save fails.” A line in the example shop might read “10:14, order 2042 marked shipped.” When the owner says an order changed by itself, the log shows what happened and when.

A bank keeps a record of every transaction for the same reason. When a customer disputes a charge, the record shows what happened.

Later sessions build on this. Session 8 shows where your hosting company keeps the logs, and what a log line must never contain. Session 10 uses a log to check the exact instructions your app sends to an AI model.

Rule of thumb: before you tell the agent something is broken, reload once and copy the error. Then check the log.

Technical debt: every shortcut is a loan

A quick solution now creates extra work later, and the extra work grows the longer you leave it.

Technical debt is the extra work you will have to do later because you chose a quick solution now instead of a better one. Like a loan, it charges interest. Every later change in that part of the app takes longer.

Maintenance managers know this well. Skipping a scheduled maintenance stop to hit this week’s shipment can be the right call. It is a loan against the machine. If nobody writes it down and schedules the make-up work, the machine eventually picks its own time to stop.

Debt comes in two kinds.

  • Deliberate debt is a shortcut you chose knowingly, with a plan to repay it. “This will not handle ten thousand products, but we need to show it to an investor on Friday.”
  • Accidental debt is a mess nobody chose. The classic case is the same rule written in three places, which then drift apart.

Agents create accidental debt quickly, because they write quickly. Ask an agent to fix the on-time rule on the order screen, and it may patch that one screen. The weekly late-shipments report keeps its own copy of the rule, with the old mistake.

You can ask about this in plain English: “Find any rule or calculation in this project that is written in more than one place.” Each result is a place where two parts of your app can disagree.

When should you pay debt down? Pay it when it blocks new work or causes errors. Pay it when you are about to change that part of the app anyway. Leave it when the app is still an experiment, or when the cleanup would cost more than it saves. And only clean up where tests exist. Without tests, you cannot tell whether the cleanup changed what the app does.

Rule of thumb: take shortcuts on purpose, and write down each one you take.

Key terms

Term Plain-English meaning
Regression Something that used to work and was broken by a later change
Test A short program that runs part of the app with a chosen input and compares the result with the expected answer
Test suite All the tests in a project, run together
Unit test A test of one rule alone, with no browser, server or database
Integration test A test of several real pieces together, such as the server and a test database
End-to-end test A test that drives a real browser through the whole app, as a user would
Test database A separate database that tests may fill and empty, never the live one
Regression test A test written for a fixed bug, so the bug cannot return unnoticed
Page memory Data held by the open page, gone when the page reloads
Browser storage Data saved in one browser on one device
Console The developer tools tab that shows errors from the app’s code
Network tab The developer tools tab that lists each request and what came back
Status code A number on each response: 200s worked, 400s were wrong or refused, 500s mean the server failed
Code review A careful reading of a set of changes, looking for mistakes no test was written for
Log A running record the app writes as it works, one line per important action or error
