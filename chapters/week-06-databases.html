Databases: Where the Data Lives — Vibe Programming, Session 6

Adapted and simplified from the first half of Scott Murff’s chapter Data and APIs, in his textbook Intro to Product Management. The ideas are his. The wording and the business examples were written for these readings.

Reading time: about 20 minutes. Class opens with a short quiz on this reading.

Learning objectives

By the end of this session you can:

  1. Name the building blocks of a database (tables, rows, columns and keys) and the three kinds of database.
  2. Turn a one-sentence description of a feature into a set of tables.
  3. Name the kinds of rule a database can enforce, and explain why a change to the design needs a migration.
  4. Predict which rows a described query will return, and spot a query that answers the wrong question.
  5. Explain why an update or a delete is dangerous, and how to protect real data.

The big idea: a prototype forgets, a product remembers

In session 2 you learned that an app has three places, and that the database is where it keeps what it must remember. In session 5 you ran the reload test and saw the difference. Data in page memory is gone on reload. Data in the database stays.

A database stores an app’s data as tables, and keeps it until someone deletes it. Everything on your screens is a view of what the database holds. The example shop’s sales dashboard is not stored anywhere as a dashboard. It is calculated from rows of orders, every time someone opens it.

Most apps have a database, because most apps must remember things between visits. A few do not. A unit converter or a simple game can forget everything when it closes. Even a simple game may want to remember the high scores, though, and then it needs somewhere to keep them.

Here is the main point of the session: the design of your data is the skeleton of your app. Every screen depends on it, and it is the hardest thing to change later.

You will not write database code. You will decide what the business needs to remember and check that the agent’s design matches the business. You will also catch a question that was answered wrongly.

This session the example shop adds a new part: stock kept at two locations. One is the freezer at the shop’s production kitchen, where the ice cream is made and the cookies are baked. The other is the freezer case and cookie shelf at the shop’s storefront, the shop on campus where customers walk in and buy. Until now the app counted all stock as one number. You will add a new kind of record to your own app as well.

Tables, rows, columns and keys

A database is a set of tables, and keys are how the tables refer to each other.

There are five building blocks.

Block What it is In the example shop
Table One kind of thing the business keeps track of Customers
Row One instance of that thing J. Park
Column One fact recorded about every row City
Primary key A column whose value is unique to each row, so the row can be pointed at Customer ID
Foreign key A column that holds the primary key of a row in another table The customer ID on an order

You already know this structure from a class roster. Each student is one row. Each fact about a student is a column. Your student ID number is a primary key: no two students share it, so it points to exactly one person.

Here are two of the shop’s tables.

Customers

Customer ID Name City
1 R. Alvarez Denver
2 J. Park Austin
3 M. Osei Boise

Orders

Order number Customer ID Product ID Quantity Promised Shipped Status
2038 2 14 2 Feb 10 Feb 14 Shipped
2039 1 11 3 Feb 12 Feb 12 Shipped
2040 2 14 1 Feb 20 Feb 19 Shipped
2041 1 11 3 Mar 3 Mar 3 Shipped
2042 2 20 1 Mar 10 (empty) Open
2043 3 14 4 Mar 12 Mar 15 Shipped

Look at the Customer ID column in the orders table. That is a foreign key. Order 2038 does not repeat “J. Park” and the customer’s city. It holds the number 2, which points to J. Park’s row. If J. Park moves, you change one row in one table. The Product ID column works the same way, pointing into a table of products.

A table looks like a spreadsheet, and that is a fair first picture. It breaks in two places.

  • A database enforces rules on every entry. A spreadsheet lets you type “seven” into a number column. A database refuses.
  • Most of a database’s usefulness comes from the links between tables. A spreadsheet does not have them.

Rule of thumb: record each fact in one place, and point to it from everywhere else.

Three kinds of database

Databases differ in where they run and who looks after them. The right kind depends on how many people use the app at once.

All three kinds below store tables, rows and keys in the same way. They differ in where the data sits and who keeps it running.

Kind Examples Where the data sits When it fits
Single-file database SQLite One file, next to the app Learning, quick prototypes, and apps used by one person on one device, such as many phone apps
Database server PostgreSQL, MySQL A program on a server that answers the app’s requests Apps with many users at once, when someone on the team can keep it running, backed up and updated
Hosted database Supabase A database server that a company runs for you Small teams that want a real database without running one. Supabase runs PostgreSQL.

A single file is simple, but it is hard to share. Many hosting companies also do not keep the files an app writes, so a single-file database on them can lose its data. A database server handles many users, but someone has to look after it. A hosted database gives you the server without the upkeep, and you pay with a monthly bill and less control.

A company makes the same choice about payroll. A very small business can run payroll from one spreadsheet. A large one may run its own payroll department. Many choose a payroll service that does the work for a fee.

The example shop uses a hosted database, like most apps in this course. Ask the agent which kind your app uses, and where its data is kept.

Rule of thumb: if several people will use your app from different devices, use a database server or a hosted one, not a single file.

From a sentence to a set of tables

The tables are the nouns of the business. For each pair, ask how many of one go with one of the other.

The whole design of tables and their links is called the schema. You can draft one from a sentence.

Start with a description of what the business needs. Underline the nouns. Then take the nouns two at a time and ask how many of one go with one of the other.

Worked example. This session the shop adds stock by location. The description is: “The shop keeps a quantity of each product at each of its locations.”

The nouns are products, locations and quantities. You already have a table of products. Now ask the question about products and locations.

  • One product can be held at many locations.
  • One location holds many products.

That is many on both sides. When that happens, you need a third table with one row for each pairing. Call it stock.

Table Columns
Products Product ID, name, price
Locations Location ID, name
Stock Product ID, location ID, quantity on hand

A row in the stock table says, “product 14, at location 2, quantity 60.” The product ID and location ID are both foreign keys.

Compare that with customers and orders. One customer has many orders, but each order has one customer. That is many on one side only, so no third table is needed. The table on the “many” side, orders, holds the foreign key.

Test yourself on one more pair. In a real shop, one order often holds several products, and each product appears on many orders. That is many on both sides again, so it needs a third table, just like stock: order lines, with one row for each product on each order.

The new tables also connect to what you already have. When the owner ships an order, the quantity on hand at one location should go down. So the shipping step now has to ask which location the package left from. A change to the data often reaches back into a flow you thought was finished.

You can check the agent’s design the same way. Ask it to list every table, its columns and its links, in plain English. Then read the list against the business. Is there a noun the business uses that has no table? Is a fact stored in two places?

Rule of thumb: before the agent builds, write the sentence, underline the nouns, and ask “how many” of each pair.

Rules live in the database, and changes are written down

The database can refuse bad data no matter which screen sent it, and its design should change only through a written, reviewable step.

Rules that hold everywhere

Session 2 taught you that a check in the browser can be skipped. The database is the last line, and it can enforce rules of its own.

Kind of rule Example in the shop
Type Quantity must be a whole number
Required An order must have a customer
Allowed values Status must be Open, Shipped or Cancelled
Range Quantity on hand cannot be negative
Link An order’s customer ID must match a real customer
Unique No two customers can share an email address

A rule in the database rejects a bad value from any screen, any script and any agent. It cannot be skipped by someone with developer tools.

Why the design is hard to change

Once real rows sit in a table, every screen, calculation and report depends on its shape.

Suppose you stored each customer’s name as one column. Later you want first and last names separately. You must rewrite every existing row and every part of the app that reads it. For a customer entered as “Front Desk, Hotel Aria,” someone has to guess.

A store has the same problem. Changing the floor plan on paper takes an afternoon. Changing it in an open store means moving every shelf and every product. Code can be rewritten quickly. Data has to be moved.

Migrations

A migration is a small file that makes one change to the schema, such as “add a locations table.” Migrations are saved in your project and applied in order.

The alternative is to click around in the database’s own website and add a column by hand. Do not do that, and do not let the agent do it. A migration has three advantages over a click.

  • It can be reviewed. It appears in a pull request, like any other change from session 3.
  • It can be repeated. A fresh database can be built by applying the migrations in order.
  • It is recorded. Your project’s history shows when the design changed, and why.

Rule of thumb: treat a change to the schema as a group 3 action. Have the agent plan it, read the plan, and review the migration before it runs.

Asking the database a question

Every question to a database is built from the same few blocks, and your job is to predict which rows come back.

A query is a question put to the database. You do not need to write one. You need to tell when the agent’s query answers a different question from the one you asked.

A query is assembled from six blocks.

Block What it does
Choose the table Where to look
Filter Keep only the rows that pass a test
Choose columns Which facts to return
Sort Put the rows in order
Limit Keep only the first few rows after sorting
Join Pair each row with its matching rows in another table

A shopping list for a busy errand is built the same way. It names the store, the items to get, the details that matter and the order to walk the aisles.

Worked example. Using the tables above, you ask: “Show the order number and quantity for J. Park’s orders that shipped late, newest first.”

  1. Table: orders.
  2. Filter: customer ID is 2, and the shipped date is after the promised date. Order 2038 passes. Order 2040 shipped a day early. Order 2042 has no shipped date, so it is not “after” anything.
  3. Columns: order number and quantity.
  4. Sort: newest first.

The answer is one row: order 2038, quantity 2.

Three things about queries surprise people.

An empty answer is not an error. Ask for R. Alvarez’s late orders and you get no rows. That is a correct answer. It also means a broken filter can look exactly like “nothing to report.”

An empty value is not zero. Order 2042 has no shipped date. It is not late, and it is not on time. A query has to say what to do with it. This is the same edge case you met in session 1.

A join drops rows that have no match. Suppose a report pairs each customer with their orders. A customer who signed up yesterday has none. Unless the query is told to keep that customer, they vanish from the list.

A query that answers the wrong question

Worked example. You ask for “each customer’s most recent order.” The agent sorts all orders by date and keeps the first one. The result is a single row: order 2043 from M. Osei.

The query ran without error. It answered “the most recent order overall.” You asked for one row per customer, which is three rows.

You catch this by predicting before you look, as in session 1. Three customers have orders, so you expect three rows. One row means the question was misread.

Why a screen gets slow

To find J. Park’s orders, the database can read every row in the table. Or it can use an index: a sorted lookup list it keeps on one column, like the index at the back of a book. An index lets it jump straight to the matching rows.

With a few hundred rows you will never notice the difference. If a screen slows down as your data grows, a missing index is the first thing to ask the agent about.

Rule of thumb: before you read a report, predict how many rows it should have.

Changing data, and protecting it

An update or a delete uses a filter to pick its rows, and a missing filter changes or erases every row in the table.

A database has four basic operations: create a row, read rows, update rows and delete rows.

The first two are low risk. The last two use the same filter block as a query. “Delete the orders where the status is Cancelled” removes a few rows. Leave off the filter, and the same instruction removes every order you have. There is no trash folder.

Four habits protect your data.

Mark, do not delete. In session 2 you told the agent to store the status Cancelled and never delete the row. Accounting works the same way. A ledger entry is never erased. A correcting entry is posted, with a reason. The shop’s dashboard is calculated from history, so the history has to stay. Marking protects a row from being erased. It does not record who changed a value, or when. That record, called an audit trail, needs the app to know who is acting. Session 7 adds logins.

Make two-table changes all or nothing. Shipping an order changes two tables. The order becomes Shipped, and the stock at one location goes down. If one change saves and the other fails, the data disagrees with itself. A database can group several changes into one transaction, so that they all happen or none do. When one action changes two tables, ask the agent to make it all or nothing. The range rule above also covers two customers buying the last pint at the same moment. The stock cannot go below zero, so the database refuses the second sale.

Back up before a change that alters or removes data. Session 3 taught you that reverting a change restores the files but not the rows. A backup is the only way back.

Do not build against real data. On the first day, your computer copy and your live app can share one database, because there is nothing to lose. Once real people use the app, that changes. Every unfinished feature you try, and every action the agent takes, would act on their data. From then on you build against a separate copy that you can wipe and refill.

That copy is filled with seed data: made-up rows that give the app something to show. Good seed data varies the way real data does. If every product in your seed data sells at the same steady pace, the dashboard will look perfect and tell you nothing.

You can also look at the data directly. The service that runs your database has a screen that shows each table and its rows. Use it to look, the way a store manager walks the aisles to check a count. Do not use it to edit.

Rule of thumb: before any update or delete, ask the agent how many rows it will touch.

Key terms

Term Plain-English meaning
Database Where an app stores its data as tables, until someone deletes it
Single-file database A database kept as one file next to the app, such as SQLite
Database server A program on a server that holds the data and answers the app’s requests, such as PostgreSQL or MySQL
Hosted database A database server that a company runs for you, such as Supabase
Table One kind of thing the business keeps track of
Row One instance of that thing
Column One fact recorded about every row
Primary key A column whose value is unique to each row, so the row can be pointed at
Foreign key A column that holds the primary key of a row in another table
Schema The whole design of the tables and their links
Migration A small file that makes one change to the schema, saved in the project and applied in order
Query A question put to the database
Filter The part of a query that keeps only the rows that pass a test
Join The part of a query that pairs each row with its matching rows in another table
Index A sorted lookup list on one column that lets the database find matching rows quickly
Audit trail A record of who changed what, and when
Transaction A group of changes that the database makes all together or not at all
Seed data Made-up rows that give the app something to show while you build
