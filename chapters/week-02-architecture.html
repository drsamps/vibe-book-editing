Architecture: The Pieces and How They Fit — Vibe Programming, Session 2

Adapted and simplified from Scott Murff’s chapter Anatomy of an Application, in his textbook Intro to Product Management. The ideas are his. The wording and the business examples were written for these readings.

Reading time: about 20 minutes. Class opens with a short quiz on this reading.

Learning objectives

By the end of this session you can:

  1. Name the three places in an app and say who controls each one.
  2. Trace one action in your app, hop by hop, from a click to a stored record and back.
  3. Explain why a check that runs only in the browser can be skipped, and where it should run.
  4. Name the service that runs each part of your app, and say what a secret key is.
  5. Write a request to the agent that says what should happen in each place.

The big idea: three places and the messages between them

In session 1 you learned to direct the agent. You asked for changes to your app, and the agent decided where each piece went. It has been making those decisions since the intro session.

This session you find out what it built. Architecture is the plan of an app: its main parts and how they connect.

Here is the main point of the session: your app is three places connected by messages, and most serious problems come from something sitting in the wrong place.

You do not need to read code to use this idea. You need a map. Once you can say which place a rule or a piece of data belongs in, you can tell the agent where to put it. You can also catch the agent when it puts something in the wrong place.

Three places

Every app is built from a browser, a server and a database, and a different party controls each one.

The browser is the program on the user’s device that shows your app, such as Chrome or Safari. Your app’s screens run inside it. The server is a computer you control that runs your app’s rules and keeps its secrets. The database is where the app stores what it must remember between visits.

Place Also called Who controls it What belongs there
Browser Frontend, client The user Screens, buttons, forms and quick checks that save the user time
Server Backend You The rules of the business, secret keys and calls to paid services
Database Storage You, through its rules Everything the app must keep: in the example shop, products, customers and orders

You will hear frontend and backend often. The frontend is what the user sees and touches. The backend is the code that runs on a computer you control.

A database stores records in tables, much like a spreadsheet. Each table has columns, and each record is one row. The example shop has a table of products, a table of customers and a table of orders. Here are two rows from its orders table.

Order number Customer Product Quantity Promised ship date Shipped
2041 R. Alvarez Honey Oat Swirl ice cream, pint 3 March 3 March 3
2042 J. Park Lemon Sugar cookies, box of 6 1 March 10 (not yet)

Think of a wholesaler that takes orders on a paper form. The customer holds the order form and can write anything on it. The order desk checks each order against the company’s rules. The warehouse holds the stock. The order form is the browser, the order desk is the server and the warehouse is the database.

Worked example. Find the three places in the example shop. The sales dashboard screen is in the browser. The shop’s rule that cancelled orders never count as sales is a business rule, so it belongs on the server or in the database. The orders themselves are rows in the database. Now find the same three places in your own app.

Rule of thumb: for any piece of your app, ask who controls the place it sits in.

Messages connect the places

The three places never share memory. They talk only by sending requests and getting responses.

A request is a message one place sends another to ask for something. A response is the reply. The browser cannot reach into the database and change a row. It has to ask.

An API is the list of requests a place agrees to answer. Your server has one, and your browser uses it. Outside services have them too. Session 9 covers APIs in detail.

Departments in a company work the same way. Sales does not walk into the warehouse and take stock off the shelf. It sends an order, and the warehouse sends back a confirmation. Every handoff is a document and a reply.

Worked example. The shop owner ships order 2042 from the table above. Follow the hops.

  1. The owner types today’s date in the ship date box and clicks Mark shipped.
  2. The browser runs a quick check: the box is not empty.
  3. The browser sends a request to the server: “Mark order 2042 shipped, today’s date.”
  4. The server checks the request again. Does order 2042 exist? Is it still open?
  5. The server asks the database to update the row for order 2042.
  6. The database saves the ship date, and replies that it is done.
  7. The server sends a response to the browser: “Saved.”
  8. The browser shows order 2042 as Shipped.

Notice that the request is checked twice, once in the browser and once on the server. The next section explains why.

In some apps the browser sends requests straight to the database for ordinary data, with no server in between. The services this course uses allow that. When it happens, the database’s own rules are the only check. Ask the agent which way your app works.

Use the trace to find a problem

The trace is also your best tool when something looks wrong.

The numbers on the shop’s dashboard are not typed in. They are calculated from the order rows each time. So a wrong number has three possible causes, one per place:

  • The stored data is wrong. A quantity was saved incorrectly in the database.
  • The rule is wrong. The calculation counts the wrong orders, such as cancelled ones.
  • The display is wrong. The right number arrives, and the screen shows it badly.

Suppose Honey Oat Swirl pints show 30 units sold per week, and you counted 24 by hand. Do not ask the agent to “fix the dashboard.” Ask where the number is calculated, and ask to see the rows it used. Then you know which place holds the problem.

Rule of thumb: never correct a calculated number on the screen. Find the place that produced it.

The trust line

The user controls the browser, so a check that runs only in the browser can be skipped.

Every piece of your app that runs in the browser is first sent to the user’s device. Browsers include a panel called developer tools. It shows a page’s code, its stored data and every request the page sends. Anyone can open it. With it, a user can read what was sent to the browser, change it, and send requests by hand.

Two consequences follow.

  • A browser check is a courtesy. It gives honest users fast feedback. It does not stop anyone who wants to get around it.
  • Anything sent to the browser is public. That includes any secret placed there by mistake.

So picture a line between the browser and everything else. On the user’s side, nothing is guaranteed. Checks that matter must run again on your side of the line, on the server or in the database.

A wholesaler already works this way. A customer can write any price on an order form. You do not bill from the customer’s number. The order desk prices the order from your own price list.

Worked example. In the example shop, an order that has shipped cannot be cancelled. The agent enforces this by turning the Cancel button grey once an order ships. That is the only check. A user opens developer tools, turns the button back on and cancels order 2041, which shipped on March 3. The three pints no longer count as sold, so the dashboard’s sales numbers are wrong. Worse, a refund may follow for ice cream the customer already has.

The fix is to enforce the rule where the data lives. The server, or a rule in the database, refuses to cancel a shipped order. Keep the grey button as well. It tells honest users what they can do.

Watch for the same mistake with access. Hiding a button or a link from some users does not stop them. A user who knows the web address can still send the request. Access is enforced only when the server or the database refuses. Session 7 covers logins and access.

Rule of thumb: if a rule protects money, data or a reported number, it must be enforced on the server or in the database.

Secrets stay on the server

A secret key is safe on the server and public the moment it reaches the browser.

Many outside services charge for use. To use one, your app sends an API key with each request. An API key is a secret string the service gives your account. It says whose account is calling, and that account gets the bill.

Your app will need one in session 10, when it calls an AI model. It may need others to send email or to reach your database with full access.

Now apply the trust line. If a key is in the browser, any user can read it with developer tools. That user can then run up your bill or read all your data. So the rule is simple. Anything that needs a secret key goes through your server. The browser asks the server, the server calls the paid service with the key, and the server passes back only the result.

A company handles its bank details the same way. The purchasing team can request a payment. Only the finance office holds the account credentials, and it makes the payment itself.

Your project keeps its secret keys in a small settings file, commonly named .env.local. That file stays on your computer and on the server. It must never be sent to GitHub, because a secret placed in a public project is published. Session 3 explains how files are kept out of GitHub.

If a secret key ever does reach the browser or a public project, treat it as public. Replace it with a new one at once, then move the work that needed it to the server.

Rule of thumb: if a user could read it in the browser, it is not a secret.

Who runs each place: the stack

You control the server and the database, but other companies own the computers they run on.

A stack is the set of technologies an app is built from. Yours has a name for each part.

Part of the app What can do the job in this course What it is
Screens and server code Next.js A toolkit for writing both the browser screens and the server code in one project
Hosting Vercel (or GitHub Pages, for an app with no server code) The company whose computers run your app and serve it at a web address
Database Supabase A company that runs your database for you, and can also handle sign-in
Project storage GitHub Where your project’s files and their history are kept (session 3)

Hosting means running an app on computers that other people can reach over the internet.

These are the services the readings use as examples. They are not the only choices, and some students will use others that do the same job. Whatever your app uses, you should be able to name the service for each row.

This is the same choice a business makes about space. A small shop rarely builds its own building. It rents the space and keeps control of the business inside it. You rent the computers and keep control of the app.

There are two copies of your app. While you build, a copy runs on your own computer at an address beginning with localhost. That name always means “this computer,” and nothing there leaves your machine. The live copy runs on the hosting company’s computers, where anyone with the address can reach it. In session 1 terms, changes to the computer copy are in groups 1 and 2. Changes to the live copy are in group 3.

Other stacks exist, and none is the only reasonable choice. The advice for a first product is to pick a well-known, well-documented one. Its problems are already known and written about. An agent also writes better code for a popular stack, because it has seen far more examples.

You speak English; the agent writes code

You direct the agent in plain English, but it does not build your app in English. It writes code: instructions in a programming language, a precise written language that computers can follow. Each place in your app has its usual languages.

Where it runs Common languages What they do
Browser (frontend) HTML, CSS, JavaScript HTML lays out what is on a screen, CSS sets how it looks, and JavaScript makes it respond to clicks
Server (backend) TypeScript, JavaScript, Python, Java, Rust and others Run the business rules and talk to the database
Both TypeScript JavaScript with extra checks added, so mistakes are caught before the app runs

Browsers understand only HTML, CSS and JavaScript, so every app’s screens end up in those three. The server side has more choice. The projects in this course use TypeScript for both.

These languages are standards for the same reason accountants share one set of accounting rules. Millions of people already know them. They are well documented, and free building blocks exist for almost any task. An AI agent has also learned from huge amounts of code written in them, so it writes them well.

You will not need to write or read any of these languages. Knowing their names helps you read the map later in this reading and follow what the agent tells you.

Rule of thumb: when something breaks, first ask which service runs the place where it broke.

Read the map, then direct by place

A file’s name and folder tell you where it runs. A request that names each place gets each piece put in the right place.

Reading the map

Your project is a set of files. You do not need to read the code inside them, and no one expects you to understand it. You are welcome to look. Just do not change a file by hand unless you know what you are doing; ask the agent to make the change instead. You can read the map without reading the code, because the stack follows naming rules.

A library works this way. A book’s call number tells you the section and the shelf before you open the book. A file’s folder and name do the same job.

Example file or folder What it holds Where it runs
app/products/page.tsx One screen. The folder path is its web address: /products Server or browser. Ask the agent.
app/api/orders/route.ts The server code that answers requests about orders Server only
components/ Screen pieces used on more than one screen Often the browser
supabase/migrations/ Each change made to the database’s tables Database
.env.local Secret keys and settings Server. Never sent to GitHub.
CLAUDE.md Your instruction file from session 1 Read by the agent. Not part of the running app.

Your file names may differ a little. The pattern will not. The ending of a file’s name tells you its language: .tsx and .ts files are TypeScript, and .md files are plain text.

To see the map yourself in the desktop app, open the Files pane: click its button, or choose it from the ⋮ menu beside the pane buttons. It shows your project’s files, and you can click one to look inside. You can also ask the agent to draw the map for you: “List every file in this project and label it browser, server, database or tools only. Explain how you decided.” Then check two of its labels against the table. That is session 1’s third question applied to a map.

Directing by place

Once you can see the places, name them in your requests. Compare two requests for the same feature.

Vague: “Let the owner cancel an order.”

By place:

  • Browser: add a Cancel button on each order that has not shipped, with a box for a reason. Show a message if the cancel fails.
  • Server: refuse to cancel an order that has already shipped. Require a reason.
  • Database: store the status Cancelled, the reason and the date. Never delete the row.
  • Dashboard: leave cancelled orders out of every sales number.

The second request says where each rule is enforced. The browser part is there for convenience. The enforcing rules sit where the user cannot reach them.

A restaurant ticket does the same thing in a kitchen. It tells the grill, the fryer and the salad station what each one makes. Nobody has to guess who does what.

When you are unsure where something belongs, ask before the agent builds. Use plan mode from session 1: “Before changing anything, explain what will run in the browser, what will run on the server, what the database will store, and where each rule is enforced.”

Rule of thumb: a request is ready when it says what happens in each place and where each rule is enforced.
